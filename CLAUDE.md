# CLAUDE.md

The ROS 2 package `syncai_driver_manager`, written in Rust (`rclrs` 0.8): a UDP bridge between ROS 2
and the quadruped robot's low-level controller (gait controller). It is a port of
`~/SyncAI-Robot-Workspace/src/syncai_driver_manager` (C++ / rclcpp), and **its external interface
must stay identical to the C++ version** (node name, executable name, parameter names, topics,
message types, QoS, service names): `syncai_robot_state` and `syncai_backend` both depend on it.
When behaviour is in doubt, the C++ version is authoritative. Deliberate exceptions: the added
`safety_locked` topic, `set_safety_lock` (`std_srvs/SetBool`), which replaces `reset_safety`, and
the sensor monitor (subscriptions to the lidar cloud / IMU named by `monitor_lidar_topic` /
`monitor_imu_topic` and to `image_raw/compressed`, a status table on stdout, nine `monitor_*`
parameters) — it adds readers only, no published interface.

**The repo root is the package itself** (`package.xml` and `Cargo.toml` are at the root); the
Workspace pulls it into `src/syncai_driver_manager` with vcstool (replacing the C++ version).
`interface.repos` and `.devcontainer/` (including the Dockerfile) are only for developing this repo
on its own; the Workspace has its own image and does not use them. There is no Makefile or
docker-compose.

## Build and test

Everything runs in the Dev Container `syncai-ros2-rust` (VS Code Reopen in Container, or
`devcontainer up --workspace-folder .`). The container's workspace root `/workspace` is the named
volume `syncai-ros2-rust_workspace` (holding build / install / log and the `src/syncai_common` that
`postCreateCommand` vcs-imports), and this repo is mounted at `/workspace/src/syncai_driver_manager`.
The host has no ROS / cargo, and no build output ends up in the host's repo directory.

```bash
docker exec syncai-ros2-rust bash -lc 'cd /workspace && colcon build --symlink-install --packages-select syncai_driver_manager'
docker exec syncai-ros2-rust bash -lc 'cd /workspace/src/syncai_driver_manager && cargo fmt --check'
docker exec syncai-ros2-rust bash -lc 'cd /workspace/src/syncai_driver_manager && cargo clippy --target-dir /workspace/build/.clippy --all-targets'
docker exec syncai-ros2-rust bash -lc 'cd /workspace/src/syncai_driver_manager && cargo test --target-dir /workspace/build/.clippy'
```

- `cargo` commands need one `colcon build` first: `/workspace/.cargo/config.toml` is generated by
  colcon-ros-cargo.
- If `syncai_common` is missing (a fresh volume), run
  `cd /workspace && vcs import < src/syncai_driver_manager/interface.repos` in the container.
- If `livox_ros_driver2` is missing (any volume created before the sensor monitor), run
  `src/syncai_driver_manager/.devcontainer/livox_msgs/import_livox_msgs.sh /workspace`. It is a
  messages-only stand-in (the real driver needs Livox-SDK2 + PCL); keep its version equal to the
  Workspace's `third-party.repos` pin.
- If `drdds` is missing (any volume created before the M20 battery), run
  `src/syncai_driver_manager/.devcontainer/drdds_msgs/import_drdds_msgs.sh /workspace`: the three
  messages `/BATTERY_DATA` needs, from the `sdk_deploy` commit the Workspace's
  `third-party-sparse.repos` pins (keep the two equal).
- Warnings from `/opt/ros2_rust_underlay/...` (rclrs itself) are not ours; ignore them.
- Before finishing, build / clippy / fmt must have zero warnings and all unit tests must pass.

## Real-robot safety (important)

- This machine is connected to the real robot: the controller is at `192.168.1.120:50051`, and
  telemetry is sent to `192.168.1.103:50010`. Other containers such as `robot01` are running ROS
  next to it (domain 1).
- When testing, **never send commands to `192.168.1.120`** (cmd_vel / set_motion_key make the robot
  move). Use loopback: `-p telemetry_recv_ip:=127.0.0.1 -p command_target_ip:=127.0.0.1`, change
  the ports, and `export ROS_DOMAIN_ID=77` (not 1 or 2).
- Only *listening* on 50010 to check whether the controller is sending telemetry is safe, but only
  one program can bind it at a time.

## Architecture (`src/driver_manager_node/`)

| File | Responsibility |
| --- | --- |
| `mod.rs` | Wiring: `robot_protocol` → that robot's parameters and link (G23: two UDP sockets + telemetry thread; M20: `M20Link`) → workers / services / monitor |
| `protocol.rs` | **Pure functions** for packet <-> struct; no sockets / Node / ROS message types; unit tested (`tests/protocol.rs`) |
| `parameters.rs` | `RobotProtocol` (declared first), `G23Parameters` (UDP, read-only) + `VelocityScale` (`MandatoryParameter`, >= 0), `M20Parameters` (read-only), `MonitorConfig` (both robots) |
| `session.rs` | UDP sockets (telemetry `listen`, command `connect`) |
| `command.rs` | `CommandLink` (sends ASCII commands), `SafetyLock` (no automatic trigger yet; `set_safety_lock` engages / releases it, and its release also sends the controller `RESET_SAFETY`) |
| `telemetry.rs` | `std::thread` that receives packets, parses them and publishes ROS messages |
| `health.rs` | **Pure** sensor bookkeeping (`SensorHealth`: rates, statuses, the stdout table); unit tested |
| `monitor.rs` | Lidar / camera subscriptions (counted only) and the `monitor` thread that prints the table |
| `publishers.rs` / `subscriber.rs` / `service.rs` | ROS interfaces |
| `drive.rs` | `Drive`: which robot the ROS interfaces drive, picked by `robot_protocol` (`g23` / `m20`) |
| `m20_protocol.rs` | **Pure** Lynx M20 functions (16-byte header + JSON, key → `MotionParam`, policy mode → `GaitParam`, cmd_vel → axis ratio); unit tested |
| `m20_link.rs` | `M20Link`: one UDP socket to the M20, a send thread (2 Hz heartbeat, 20 Hz axis command with a cmd_vel timeout) and a receive thread (logs `MotionState` and `Gait`) |
| `m20_battery.rs` | **Pure**: the M20's `/BATTERY_DATA` packs combined into one `protocol::Battery`; unit tested |
| `m20_battery_forwarder.rs` | M20 only: subscribes `battery_topic` (`drdds/msg/BatteryData`) on its own Worker and publishes `battery_state` with the G23's builder (`publishers::battery_state_msg`) |

**Params files.** `params/driver_manager_params.yaml` holds only what every model shares (the
monitor's period and timeouts); everything that is one robot's is in
`params/models/<robot_model>.yaml`, which the launch loads after it (`robot_model` from the INI,
`g23` when missing). `g23.yaml`: `robot_protocol`, the UDP endpoints, the Livox monitor topics and
`scale_*`; `m20.yaml`: `robot_protocol`, `motion_host_*`, `max_*`, `cmd_timeout`, `battery_topic` and the
vendor's monitor topics. The launch **refuses a model with no file** (the code defaults would bind on
`0.0.0.0:50012` with every scale 1.0 and look healthy). A new robot-specific key goes in the model
files, not the shared one.

With `robot_protocol: m20` (the launch loads `params/models/m20.yaml` when the INI says
`robot_model: m20`) neither G23 socket nor the telemetry thread exists, and the G23's
`telemetry_*` / `command_*` / `scale_*` are not declared (nor the M20's `motion_host_*` / `max_*` /
`cmd_timeout` / `battery_topic` on a G23: `robot_protocol` is declared first and picks the set; the G23's
`VelocityScale` lives in `Drive::G23`); only motion keys "0" / "2" / "4" (ESTOP = `2/22 MotionParam 2`, Soft Emergency Stop; like the G23's, the link stays up), `set_policy_mode` 0 / 1 (the
Basic / Stair gait, `2/23 GaitParam` 0x1001 / 0x1003) and `cmd_vel` do anything, every other call
answers `success: false`. `battery_state` is published on **both** robots, from one
builder (`publishers::battery_state_msg`): on a G23 from the telemetry's `BMS_V2`, on an M20 from
the vendor's `/BATTERY_DATA` (two packs combined, `m20_battery.rs`); keep the two identical in
topic, type and QoS, since `syncai_robot_state` and charge.xml's `WaitForCharging` read either.
The M20's lidar and battery topics are absolute (`/LIDAR/POINTS_UDP`, `/IMU`, `/BATTERY_DATA`)
because its vendor stack publishes them without a namespace — the only names this node uses
outside `/<robot_id>`. The M20's motion host is `10.21.31.103:30000` on its internal LAN:
**the same real-robot rule applies to it** — test against `motion_host_ip:=127.0.0.1`.

Threads: `cmd_vel` has one rclrs Worker, and the four services share one Worker (equivalent to the
C++ version's two MutuallyExclusive callback groups; the two workers run in parallel). Telemetry has
its own `std::thread` on a G23; on an M20, `M20Link` has two (send, receive) instead, and the battery forwarder a Worker of
its own. The lidar / camera subscriptions have a third Worker, and the status table
its own `std::thread`; all of them write or read the shared `Arc<SensorHealth>`. New packet parsing
logic goes in `protocol.rs`, with unit tests.

Unit tests live in `src/driver_manager_node/tests/<module>.rs`, one file per module, and each module
ends with `#[cfg(test)] #[path = "tests/<module>.rs"] mod tests;`. They stay unit tests (a child
module, so `use super::*` reaches private items); the repo-root `tests/` that Cargo uses for
integration tests is not used, because this crate is bin-only and has no public API to test.

## rclrs pitfalls (all hit in practice)

- **Params YAML keys do not expand wildcards**: only `/**` or the node's full name match.
  `/**/driver_manager` is silently ignored and everything falls back to defaults. This package's
  YAML uses `/**:`.
- **Worker = callback group**: callbacks from `node.create_*` all queue on the executor's single
  thread; callbacks from `worker.create_*` run on that worker's own thread. The callback shape is
  `FnMut(&mut Payload, Msg)`.
- **No SIGINT handler**: Ctrl-C ends the process immediately and `Drop` does not run.
  A process backgrounded with `&` in a non-interactive shell script ignores SIGINT; send SIGTERM to
  stop it.
- **`ros-env` versions**: the package uses `ros-env` 0.2 while rclrs uses 0.3 internally, and their
  message types are incompatible. Do not use rclrs helpers that return message types (e.g.
  `Time::to_ros_msg`); build them yourself from `Time::nsec`.
- The `Message` trait under `rclrs::*` is `rosidl_runtime_rs::Message`.
- Message packages do not go in `Cargo.toml` but in `<depend>` in `package.xml`; without it
  `ros_env::<pkg>` does not exist.
- `launch/` and `params/` are installed to share via `[package.metadata.ros] install_to_share` in
  `Cargo.toml`.

## Conventions

- Everything is written in English: code and config comments (Rust, Cargo.toml, Dockerfile,
  devcontainer.json, toml…), log messages, and docs such as README / CLAUDE.md. Log messages carry a
  `[Module]` prefix (e.g. `[Telemetry]`, `[DriverManagerNode]`).
- Formatting follows the root `rustfmt.toml` (max_width 100); Cargo.toml enables
  `unsafe_code = "forbid"` and `clippy::all`.
- Commits use Conventional Commits (`.github/prompt/copilot-commit-message-instructions.md`), in
  English.
- `syncai_common` is another repo that vcstool pulls into the container workspace (it is not in this
  repo); change message definitions in SyncAI-Robot-Interface.
- Known open questions (left as TODOs in the source; need the real robot): the sign of `angular.z`,
  IMU_RPY units, joint order, and the safety trigger conditions (battery < 20%, JOINT_TEMP
  overheating).
